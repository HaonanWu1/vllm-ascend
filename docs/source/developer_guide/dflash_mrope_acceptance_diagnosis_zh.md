# Qwen3-VL-4B DFlash 低接受率定位

日期：2026-09-10。环境与 checkpoint 同 `dflash_mrope_latest_validation_zh.md`。

## 当前结论

**在已检查的图像样例上，低接受率主要表现为 checkpoint 自身的候选预测与主模型不匹配，尚未发现 Ascend 的位置、缓存或接受流程导致该低接受率的证据。**

这个判断不只依赖最终生成文本一致：本次完全绕开 vLLM-Ascend，使用 CPU Hugging Face 主模型重新计算特征，再加载 checkpoint 保存的 `dflash.py` 和权重，复现了低接受率；按实际接受/拒绝规则推进 anchor 后，还与两个实机用例的候选、接受计数逐项一致。

这能够定位到“草稿在当前输入上预测得不好”，但不能仅凭一个图像样例进一步断言训练代码有错、训练轮数不够或模型已经过拟合。

## 接受率的含义

此前 3.30% 的统计为：36 个接受 token / 1,092 个候选 token。共 156 个草稿块，每块 7 个候选，因此平均每块接受约 0.231 个候选。

该混合请求用例各候选位置的连续通过数为 `[32,4,0,0,0,0,0]`：

- 第一候选通过率：32 / 156 ≈ 20.51%。
- 前两个候选同时通过率：4 / 156 ≈ 2.56%。
- 已通过第一候选的块中，第二候选继续通过的比例：4 / 32 = 12.5%。

这些计数是连续前缀通过数，不能把后面的位置计数当作独立的 token 准确率。第一候选不同，就无法继续接受同一块后面的候选。DFlash 的目标是匹配主模型的具体 token 顺序，而不只是产生语义正确的另一种回答。

## 独立参考排查

本次诊断没有调用 Ascend proposer、NZ 缓存、Ascend m-RoPE 或拒绝采样器。

1. 重建与实机相同的红色方块图片和问题，使用 CPU HF 主模型计算 88-token prompt 及其 64-token 延续的隐藏状态。
2. 取 HF `hidden_states[4,11,19,26,33]`，独立构造草稿输入。
3. 使用 checkpoint 自带实现、原始权重、主模型 embedding 和 LM head 计算候选。
4. 分别检查任意 anchor 的草稿质量，以及按接受结果推进 anchor 的实际解码路径。

| 检查 | 结果 |
| --- | --- |
| HF 与实机 context 三轴位置 | 完全一致 |
| HF 与实机五组目标特征的拼接结果 | 相对 RMS 误差约 0.1969%，余弦相似度 0.99999808 |
| HF 主模型在实机生成路径上的条件 argmax | 64 / 64 token 与实机一致 |
| anchor 和 MASK embedding | 完全一致 |
| 相同实机输入下，CPU 草稿与实机草稿输出经共享 LM head 后的 top-1 | 8 / 8 位置一致，包含全部 7 个候选 |

特征比较使用 FP64 做误差归约，避免长向量 FP32 余弦计算的累计舍入误差。主模型和草稿的主要推理比较仍使用 FP16。

第一块的 anchor 已经是 `The`，后续七个候选解码为：

| 来源 | 后续 token 解码 |
| --- | --- |
| 主模型 | `large square in the image is **` |
| Ascend 草稿 | `red red a a a a\n` |
| checkpoint CPU 参考，使用相同输入 | `red red a a a a\n` |

因此第一候选就无法接受。草稿识别出“红色”并不够：主模型选择的是 “The large square…”，草稿必须跟随这一具体序列。重复词和后续位置的无效预测也表明问题不只是最后一个标点不同。

精度补充检查对各精度重新建立草稿实例并严格加载权重，避免跨精度复用已舍入的旋转频率。FP16、BF16、FP32 都没有修复前六个错误候选；BF16 仅改变了末尾标点。这是首块的控制实验，不代表全数据集的精度比较。

## 接受流程重放

在同一图像回答的 64-token 路径上，取 57 个具有完整七候选标签的 anchor，完全独立计算草稿：

- 各位置独立命中数：`[9,9,4,3,1,0,0]`。
- 各位置连续前缀通过数：`[9,1,0,0,0,0,0]`。
- 平均连续接受 0.1754 token / 块，候选接受比例约 2.506%。

第二位置单独命中了 9 次，但只有 1 次同时通过第一位置，说明连续接受要求确实放大了早期预测错误。57 个重叠窗口来自一个样例，2.506% 不是数据集指标，也不能直接与不同调度路径的线上指标相减。

进一步按“接受前缀后加入主模型 token”的规则推进 anchor，得到以下严格可比结果。计数均包含一次预热和一次记录轮次：

| 实机用例 | CPU 独立重放与实机的共同结果 |
| --- | --- |
| 单图、16-token 输出 | 26 个草稿块，182 个候选，接受 4 个；各位置 `[2,2,0,0,0,0,0]` |
| 三个相同图像请求、异步调度、32-token 输出 | 156 个草稿块，1,092 个候选，接受 36 个；各位置 `[30,6,0,0,0,0,0]` |

这两组计数完全相同，支持当前低接受率不是实机把本应通过的候选错误拒绝。它仍不是对所有请求、全部草稿张量和所有调度组合的穷尽证明。

## 为什么 checkpoint 在这里表现不好

已知训练参数：数据路径指向 `regenerated/textvqa-train-10k-qwen3-vl-4b.jsonl`，HF target backend，三轮、global step 3750、学习率 2e-4、最多 32 个 anchor、gamma=4，且 `eval_data_path=None`。配置名中的层数默认值没有覆盖 checkpoint 的五层结构。

当前训练源码对数据中的后续 token 做同位置交叉熵监督，排除 anchor。数据文件名说明它是 Qwen3-VL 重生成的 TextVQA 数据，不能据此当作未经重生成的人工短答案，也不能仅凭文件名确认其生成温度、提示模板和质量。

当前测试包含合成方块描述和通用文本，任务与 TextVQA 训练域有差异。因此**训练域与当前任务不匹配是优先核查的解释**。但“数据量不够”“欠拟合”“过拟合”目前都还没有训练曲线或验证集结果支持，不能当作确定原因。

checkpoint 保存的是另一台机器的训练数据路径；本环境尚未定位到该 JSONL、对应图片和训练日志。当前证据也没有证明训练时目标权重及依赖版本与本机完全相同。

下一步应取训练域内样本和未参与训练的同域样本，使用相同的独立参考，比较第一位置准确率、各位置独立准确率和连续接受长度，并结合 train/eval loss：

- 同域表现好、当前描述任务差：重点扩充训练任务和回答形式。
- 训练样本与同域验证都差：重点检查训练收敛、监督有效 token、目标特征与配置一致性。
- 训练样本好、同域验证差：再评估过拟合。

在这些结果出来前，不建议根据当前 3.3% 就直接决定增加 epoch 或重新修改 m-RoPE。
